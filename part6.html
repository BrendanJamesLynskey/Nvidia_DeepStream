01

Metadata is the product

Every plugin discussed so far — decode, mux, PGIE, tracker, SGIE, analytics, OSD — ultimately exists to do one thing: convert pixels into structured meaning. The pixels themselves stay resident in GPU memory as an NvBufSurface and are rarely touched directly by application code. What your application actually reads, filters, counts, publishes and reacts to is the batched metadata that Gst-nvstreammux attaches to every buffer and that every downstream element enriches in place.

This is the practical consequence of the "zero-copy" architecture from Part 02: because pixels never leave GPU memory, the only cheap, CPU-visible thing riding the pipeline is metadata — small, structured, and designed to be walked from a single C or Python callback. Understanding this graph is understanding how to write a DeepStream application at all.

Why it matters

Almost every line of custom DeepStream application code — drawing a custom overlay, filtering detections by class, counting objects, publishing an event — is a read or write against this metadata graph, not a CUDA kernel. Get the hierarchy right and the rest of the SDK becomes approachable.

02

The NvDsBatchMeta hierarchy

A single GstBuffer carries two separate things once it leaves nvstreammux: the pixel data (an NvBufSurface) and a parallel metadata tree rooted at NvDsBatchMeta, retrieved with gst_buffer_get_nvds_batch_meta(). Every plugin after the muxer adds to this tree rather than replacing it — the tracker stamps object_id, an SGIE hangs a classifier result off each object, and analytics plugins attach their own user metadata.

The tree grows — it is never rebuilt. Each object's classifier_meta_list can carry results from several SGIEs; each frame or object can carry several independent NvDsUserMeta entries side by side.

04

Lifecycle & pools

Metadata objects are never malloc'd ad hoc. They are acquired from pre-allocated pools owned by the batch meta — nvds_acquire_frame_meta_from_pool(), nvds_acquire_obj_meta_from_pool(), nvds_acquire_user_meta_from_pool() — attached to the tree, reference-counted as the buffer flows through multiple threads and plugins, and returned to the pool once the buffer is done with, rather than freed to the heap.

This is what makes metadata safe and cheap at video rates: no per-frame heap churn, no allocator contention between pipeline threads, and a bounded, predictable memory footprint set by the pool size at nvstreammux configuration time. When you attach custom data via NvDsUserMeta, you plug into the same discipline — the struct itself carries a meta_type, a user_meta_data pointer, and a copy_func/release_func pair so the pool machinery knows how to duplicate or tear down your payload without knowing what it is.

Golden rule

Always acquire metadata through the pool APIs, never malloc or new it directly and attach the pointer. Hand-rolled allocations bypass the ref-counting and lifetime guarantees the whole metadata system depends on — the classic symptom is a crash or corrupted frame under load that never shows up in light testing.

05

Accessing metadata — buffer probes

Applications read and modify the metadata graph through a buffer probe: a callback attached to a pad (commonly the tracker's or an SGIE's src pad) that fires on every buffer crossing it. Inside the probe you pull NvDsBatchMeta off the buffer and walk frame_meta_list → obj_meta_list as a linked list.

tracker_probe.py
def tracker_src_pad_probe(pad, info, u_data):
    gst_buffer = info.get_buffer()
    batch_meta = pyds.gst_buffer_get_nvds_batch_meta(hash(gst_buffer))

    l_frame = batch_meta.frame_meta_list
    while l_frame is not None:
        frame_meta = pyds.NvDsFrameMeta.cast(l_frame.data)
        l_obj = frame_meta.obj_meta_list
        while l_obj is not None:
            obj = pyds.NvDsObjectMeta.cast(l_obj.data)
            print(f"src={frame_meta.source_id} id={obj.object_id} "
                  f"class={obj.class_id} conf={obj.confidence:.2f}")
            try:
                l_obj = l_obj.next
            except StopIteration:
                break
        try:
            l_frame = l_frame.next
        except StopIteration:
            break
    return Gst.PadProbeReturn.OK
tracker_probe.c
static GstPadProbeReturn
tracker_src_pad_probe(GstPad *pad, GstPadProbeInfo *info, gpointer u_data)
{
    GstBuffer *buf = (GstBuffer *)info->data;
    NvDsBatchMeta *batch_meta = gst_buffer_get_nvds_batch_meta(buf);

    for (NvDsMetaList *l = batch_meta->frame_meta_list; l; l = l->next) {
        NvDsFrameMeta *frame_meta = (NvDsFrameMeta *)l->data;
        for (NvDsMetaList *o = frame_meta->obj_meta_list; o; o = o->next) {
            NvDsObjectMeta *obj = (NvDsObjectMeta *)o->data;
            g_print("src=%d id=%lu class=%d conf=%.2f\n",
                    frame_meta->source_id, obj->object_id,
                    obj->class_id, obj->confidence);
        }
    }
    return GST_PAD_PROBE_OK;
}
06

Extending it — NvDsUserMeta

The metadata graph is deliberately open-ended. Any plugin or application can hang its own payload off a frame or an object via NvDsUserMeta, without the SDK needing to know what that payload means.

  • meta_type — an integer identifying the payload's kind; custom types must start at or above NVDS_START_USER_META so they never collide with the framework's own reserved values.
  • user_meta_data — an opaque pointer to your payload, acquired from the batch meta's user-meta pool via nvds_acquire_user_meta_from_pool().
  • copy_func / release_func — you supply these so the pool machinery can duplicate or free your payload correctly during batch-meta copy and recycle — the same discipline as every other pooled struct.
  • Two attach points — frame-level (nvds_add_user_meta_to_frame) for scene-wide results, object-level (nvds_add_user_meta_to_obj) for per-track results.
  • In practice — nvinfer's output-tensor-meta property attaches raw, unparsed inference tensors this way; nvdsanalytics attaches its rule results this way; applications use it to carry state (an event ID, a computed score) forward as far as nvmsgconv, which reads user meta to build custom message payloads.
07

Gst-nvdsanalytics — rules on tracks

Gst-nvdsanalytics sits after the tracker and evaluates simple, declarative spatial rules against tracked objects — all defined per-stream in a config file, with no code required. Four rule types: ROI filtering (only objects inside a polygon count downstream), line-crossing counting with direction, overcrowding (occupancy of a region against a threshold), and direction detection (which way a track is moving).

Results attach as user meta, not as a new detection type: per-object NvDsAnalyticsObjInfo (which ROI it's in, its crossing/direction state) and per-frame NvDsAnalyticsFrameMeta (aggregate counts, overcrowding status) — both readable from the same probe pattern as any other metadata.

08

From metadata to action

Everything downstream of the tracker is, in the end, a consumer of this graph. Gst-nvdsosd reads NvDsDisplayMeta/NvDsObjectMeta to draw boxes, labels and lines — it never inspects pixels to find objects, it's told exactly where they are. Gst-nvmsgconv reads frame and object meta (plus any user meta an app or analytics plugin has attached) and serialises it into an event payload, the subject of Part 07. And your own probe can inspect the same graph to trigger smart-record clip capture or arbitrary custom application logic.

09

Takeaways

  • The pipeline's real product is the NvDsBatchMeta → NvDsFrameMeta → NvDsObjectMeta → NvDsClassifierMeta hierarchy, built by nvstreammux and enriched by every plugin after it; pixels live separately in NvBufSurface.
  • Metadata comes from pools, never malloc — that's what keeps it safe and cheap at video rates across multiple threads.
  • The buffer probe attached to a pad is your API into the graph, in both C and Python (pyds) — walk frame_meta_list then obj_meta_list.
  • NvDsUserMeta is the extension point — raw tensors, analytics results, or your own application state, all carried the same way with a meta_type and copy/release functions.
  • Gst-nvdsanalytics turns tracked objects into rule-based events — ROI, line-crossing, overcrowding, direction — entirely from config, attached as user meta like everything else.
