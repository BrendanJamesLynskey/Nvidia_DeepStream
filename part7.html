01

The last mile

Everything in Parts 05 and 06 — tracked objects, analytics-rule events, tensor metadata — lives in NvDsBatchMeta inside the process. That's fine for on-screen bounding boxes, but a security desk, a BI dashboard or a control-room alert has no way to reach into GPU memory. Metadata that never leaves the box is worthless outside it.

This part covers the four pieces that close that gap:

  • Serialising events into a structured payload (Gst-nvmsgconv).
  • Publishing that payload to a message broker (Gst-nvmsgbroker).
  • Recording the video around an event as an evidence clip (Smart Record).
  • Receiving commands back from the cloud — and reconfiguring the pipeline live via REST.

Together they turn a DeepStream instance from an isolated video pipeline into one node in a managed, cloud-connected fleet.

02

Gst-nvmsgconv — metadata to payload

Sits after the analytics stage and converts NvDsEventMsgMeta — the event-level metadata a probe or nvdsanalytics attaches to a frame — into a serialised payload, JSON or protobuf, ready to hand to a broker.

  • Full / DeepStream schema — rich, per-object events carrying sensor identity, place/location context, and analytics-module detail (which rule fired, direction, ROI). This is what a video-analytics platform expects.
  • Minimal schema — a compact per-frame or per-object payload with just the essentials (timestamp, sensor id, object list). Lower bandwidth, useful for high-frequency telemetry or constrained links.
  • Custom schema — supplied via a custom conversion library (msg2p-lib) implementing the msgconv interface, for teams whose downstream system expects its own event shape.

03

Gst-nvmsgbroker — to the broker

Takes the serialised payload from nvmsgconv and hands it off asynchronously to an external message system, via a pluggable protocol adapter — a shared library selected with proto-lib plus a broker connection-str. Swapping brokers is a config change, not a pipeline rewrite.

AdapterProtocol libraryTypical use
Kafkalibnvds_kafka_proto.soHigh-throughput event streaming into a data platform; consumer groups, topic partitioning, replay from offset.
AMQP (RabbitMQ)libnvds_amqp_proto.soExchange/queue routing with delivery guarantees; enterprise message-bus integration.
MQTTlibnvds_mqtt_proto.soLightweight pub/sub over constrained or wireless links; large fan-out of edge devices to a broker.
Azure IoT Hublibnvds_azure_proto.soManaged cloud ingestion with device identity, twin state and built-in cloud→edge command channel.
Redislibnvds_redis_proto.soLow-latency pub/sub or stream ingestion for local/edge-cluster fan-out ahead of a heavier pipeline.

Sends are non-blocking: nvmsgbroker queues the payload and returns a delivery status via callback, so a slow or unreachable broker degrades message delivery rather than stalling video processing upstream.

04

Wiring it into the pipeline

The messaging path taps off the main pipeline rather than sitting inline — a tee after the analytics stage feeds display/encode on one branch and msgconv/msgbroker on the other, so a broker hiccup can't touch the video path.

The event-generating probe is application logic: it inspects NvDsAnalyticsFrameMeta or object state, decides whether this frame is newsworthy, and only then allocates and attaches an NvDsEventMsgMeta. Rate-limiting and de-duplication (don't re-report the same object crossing the same line every frame it's tracked) live here — msgconv/msgbroker will happily serialise and send everything you give them.

05

Smart Record

Messaging tells you that something happened; Smart Record captures the video of it. Gst-nvurisrcbin (single source) and Gst-nvmultiurisrcbin (multi-source) each keep a rolling, encoded-video ring buffer in memory per stream, continuously overwriting itself.

  • An application trigger — an analytics event, or a command arriving from the cloud — calls the smart-record start API.
  • The written clip includes pre-event history already sitting in the ring buffer, plus a configurable post-event tail, so the recording captures the run-up to the trigger, not just the moment after it.
  • Output is a standalone mp4 file on disk, named and indexed for later retrieval — the standard pattern for evidence/incident clips tied to a specific alert.

Because the trigger can originate locally or from the cloud, Smart Record is the natural companion to bidirectional messaging: an operator watching a dashboard alert can request the clip on demand, not just review whatever the edge decided to save.

06

Bidirectional / cloud-to-edge

nvmsgbroker isn't send-only. The same protocol adapters that publish events can also subscribe — the plugin supports a receive/consume path so a cloud service can push commands down to the device, not just receive telemetry from it.

  • Start/stop recording — trigger Smart Record remotely, e.g. after an operator reviews a low-confidence alert and wants the full clip.
  • Change configuration — adjust an ROI, detection threshold or analytics rule without touching the device physically.
  • Acknowledge an alert — close the loop so the edge knows a human has seen the event, useful for de-duplicating repeat notifications.

This is the classic IoT device pattern: Azure IoT Hub models it explicitly with cloud-to-device messages and device twins; Kafka-based deployments achieve the same shape with a dedicated command topic the edge process subscribes to alongside its publish topic.

In practice

Treat the command channel with the same rigour as any external input — validate payloads, authenticate the sender, and rate-limit what a single command can trigger. A misconfigured or spoofed "start recording on every camera" command is a denial-of-service against your own storage.

07

Dynamic streams & the REST API

Gst-nvmultiurisrcbin exposes a REST API for runtime source management — the same lever a cloud command channel typically pulls, but usable directly for orchestration tooling too.

  • Add a stream — onboard a new camera by URI without stopping or rebuilding the pipeline.
  • Remove a stream — decommission a source cleanly, freeing its batch slot for reuse.
  • Change parameters — adjust per-source settings (e.g. ROI, sync behaviour) live.

It's the same building block underneath NVIDIA Metropolis Microservices — the Video Storage Toolkit (VST) and related media/analytics microservices use it to provision sources declaratively in cloud-native deployments.

08

Edge-to-cloud reference architecture

The full loop: sensors in, insight out, control back down — with Metropolis Microservices as the cloud-native scaffolding around the DeepStream pipeline itself.

Nothing here is exotic — it's the same mux/infer/analytics pipeline from Parts 03–06, with a publish leg and a subscribe leg bolted on. What changes at scale is orchestration: Metropolis Microservices wrap that single-box pipeline in the provisioning, storage and lifecycle tooling a fleet of them needs.

09

Takeaways

  • Gst-nvmsgconv serialises NvDsEventMsgMeta into JSON or protobuf, in Full/DeepStream, Minimal or custom schema — per event, not per frame.
  • Gst-nvmsgbroker publishes via pluggable protocol adapters — Kafka, AMQP, MQTT, Azure IoT Hub, Redis — selected by config, not code change.
  • Events are generated by application probes; rate-limit and de-duplicate there, since msgconv/msgbroker will send whatever they're given.
  • Smart Record keeps a ring buffer per stream and writes trigger-driven mp4 clips with pre-event history — the standard evidence-clip pattern.
  • Messaging is bidirectional: the cloud can push start-recording, reconfigure and acknowledge commands back down to the edge.
  • nvmultiurisrcbin's REST API adds/removes streams and tunes parameters live, underpinning elastic, Metropolis-Microservices-based deployments.
