01

Four ways to build

Every DeepStream pipeline is the same GStreamer graph underneath — nvstreammux → nvinfer → nvtracker → nvinfer → nvdsosd → sink, with variations. What differs is how much of that graph you author by hand, in what language, and how quickly you can iterate. Four entry points cover essentially every use case.

deepstream-app (config file)

No code at all — a text config file with [source], [streammux], [primary-gie], [sink] groups drives the reference application. Fastest path to a working multi-stream pipeline; the natural default for standard detect → track → classify → display flows.

C/C++

Direct GStreamer + DeepStream API calls — gst_element_factory_make, property setters, pad probes. Maximum control and the lowest overhead; the only path when you need custom elements, tight latency budgets, or behaviour the config file can't express.

Python (pyds)

The same GStreamer graph built via gst-python, with metadata read and written through the pyds bindings. Rapid prototyping and metadata-heavy logic — the natural choice when the interesting work is in the probe callback, not the pipeline topology.

Graph Composer / Service Maker

A visual low-code editor over the GXF runtime for graph-based authoring, or the Service Maker API for building a pipeline in a handful of lines (C++, and Python since 7.1). Visual iteration or minimal boilerplate over raw GStreamer plumbing.

In practice

Most teams start with deepstream-app to validate the pipeline shape and models, then drop to C/C++ or Python only for the parts that need custom logic — a full hand-rolled pipeline from scratch is rarely the first move.

The config-driven reference app

deepstream-app -c config.txt is the sample application that ships with the SDK, and it is capable enough to be a production deployment on its own — no code is compiled. It reads a single INI-style file where each [group] configures one part of the pipeline it builds internally: sources, mux, inference engines, tracker, on-screen display, tiling and sinks.

num-sources=1

[streammux]
batch-size=4                  # == number of active sources
batched-push-timeout=40000    # microseconds
width=1920

live-source=1

batch-size=4

Multiple [sourceN], [secondary-gieN] and [sinkN] groups compose freely — a four-camera, two-classifier, tiled-and-recorded deployment is still just more groups in the same file, no recompilation required.

03

The C/C++ path

Below the config file is the same API the reference app itself is built on: standard GStreamer element creation and linking, plus DeepStream-specific elements and metadata structures. A minimal pipeline is a handful of calls — create elements, set properties, link them, attach a pad probe to read NvDsBatchMeta, and run a GMainLoop.

deepstream_test1_app.c (skeleton)
#include <gst/gst.h>
#include <gstnvdsmeta.h>

int main(int argc, char *argv[]) {
    GstElement *pipeline, *source, *mux, *pgie, *tracker, *osd, *sink;
    GMainLoop  *loop;

    gst_init(&argc, &argv);
    loop = g_main_loop_new(NULL, FALSE);

    pipeline = gst_pipeline_new("ds-pipeline");
    source   = gst_element_factory_make("uridecodebin", "src");
    mux      = gst_element_factory_make("nvstreammux", "mux");
    pgie     = gst_element_factory_make("nvinfer", "pgie");
    tracker  = gst_element_factory_make("nvtracker", "tracker");
    osd      = gst_element_factory_make("nvdsosd", "osd");
    sink     = gst_element_factory_make("nveglglessink", "sink");

    g_object_set(G_OBJECT(mux), "batch-size", 1, "width", 1920, "height", 1080, NULL);
    g_object_set(G_OBJECT(pgie), "config-file-path", "pgie_config.txt", NULL);

    gst_bin_add_many(GST_BIN(pipeline), source, mux, pgie, tracker, osd, sink, NULL);
    gst_element_link_many(mux, pgie, tracker, osd, sink, NULL);

    /* probe reads NvDsBatchMeta off every buffer reaching the OSD */
    GstPad *sink_pad = gst_element_get_static_pad(osd, "sink");
    gst_pad_add_probe(sink_pad, GST_PAD_PROBE_TYPE_BUFFER, osd_sink_pad_buffer_probe, NULL, NULL);

    gst_element_set_state(pipeline, GST_STATE_PLAYING);
    g_main_loop_run(loop);
}

The sample apps deepstream-test1 through deepstream-test5 are the canonical learning ladder for this path: test1 is single-stream detection, escalating through multi-source muxing, tracking, and secondary classification, to test4 which adds an nvmsgconv/nvmsgbroker pair for schema payloads and IoT delivery, and test5 which assembles a config-driven, production-shaped application with all of the above.

04

The Python path

The Python bindings — pyds — expose the same NvDsBatchMeta/NvDsFrameMeta/NvDsObjectMeta structures used in C, wrapped for access from a gst-python pipeline. The pipeline-building code looks almost identical to the C version; the payoff is in the probe callback, where Python's ergonomics make metadata-heavy logic — the pattern covered in Part 06 — much faster to write and iterate on.

deepstream_test1.py (probe excerpt)
import pyds

def osd_sink_pad_buffer_probe(pad, info, u_data):
    gst_buffer = info.get_buffer()
    batch_meta = pyds.gst_buffer_get_nvds_batch_meta(hash(gst_buffer))

    l_frame = batch_meta.frame_meta_list
    while l_frame is not None:
        frame_meta = pyds.NvDsFrameMeta.cast(l_frame.data)
        l_obj = frame_meta.obj_meta_list
        while l_obj is not None:
            obj_meta = pyds.NvDsObjectMeta.cast(l_obj.data)
            print(f"id={obj_meta.object_id} class={obj_meta.class_id}")
            l_obj = l_obj.next
        l_frame = l_frame.next
    return Gst.PadProbeReturn.OK

The deepstream_python_apps repository mirrors the C test-app ladder and is the primary reference. The trade-off against C/C++ is the usual one: faster to write and easier to debug, but the pipeline's steady-state throughput is set by the native GStreamer/TensorRT elements either way — Python cost only shows up in the probe, where the GIL and per-call binding overhead matter if you're doing heavy per-object work at high batch size and frame rate.

Since DeepStream 7.1, Service Maker is also available in Python, not just C++: a higher-level abstraction over raw GStreamer that builds a working pipeline — sources, inference, tracker, sink — in a handful of method calls rather than manual element creation and linking, for teams that want less boilerplate without leaving Python.

05

Graph Composer & GXF

Graph Composer is a visual, low-code editor for building DeepStream pipelines as graphs rather than code or config text: drag components onto a canvas, wire their ports together, and edit parameters in a property panel. Underneath, it targets the GXF (Graph Execution Framework) runtime — a component-based execution engine with its own extension model — so a Graph Composer graph is a GXF graph with DeepStream-specific extensions (source, inference, tracker, OSD components) registered into it.

The built-in container builder packages the finished graph, its extensions and dependencies into a deployable container image targeting a specific platform — Jetson (JetPack) or discrete GPU — closing the loop from visual authoring to a shippable artefact without a separate manual Docker build. It's the right tool when a graph-native, visual iteration workflow matters more than hand-written pipeline code, or when non-programmers on a team need to compose and tune pipelines directly.

06

Packaging & deployment

Whichever way the pipeline was built, it ships the same way most GPU workloads do: as a container, pulled from NGC (nvcr.io/nvidia/deepstream), with the model repository and TensorRT engine files either baked into the image or mounted at runtime so engines can be rebuilt per-target without a new image.

On Jetson, the container's L4T/JetPack version must match the board's flashed JetPack release — this is the single most common "it worked on my dGPU box but not the Jetson" failure. At larger scale, Kubernetes with Helm charts handles multi-node, multi-GPU orchestration and restart/scaling policy, and Metropolis Microservices packages common DeepStream pipeline patterns as ready-to-compose services (API-fronted, multi-stream) for teams that don't want to own pipeline code at all. Multi-GPU scale-out is then just more replicas — each pipeline instance owns a fixed set of streams and a gpu-id, and the orchestration layer handles placement.

07

Performance tuning

The metric that matters is rarely single-stream latency in isolation — it's aggregate streams × fps at a latency budget, and by extension, cost-per-stream on a given GPU. Every knob below trades one of throughput, latency or accuracy for another.

KnobWhereEffect
batch-sizenvstreammux, nvinferShould track the number of live streams; under-sized batches waste GPU parallelism, over-sized batches add wait latency for the batch to fill
intervalnvinfer (PGIE)Skip N frames between detector runs; the tracker predicts through the gap. The single biggest lever for headroom on GPU-bound pipelines
Precision: FP16 / INT8nvinfer engine buildRoughly 2×/4× throughput over FP32 on Tensor Core hardware; INT8 needs a calibration cache and costs some accuracy
DLA offloadnvinfer, Jetson onlyMoves inference off the GPU onto the Deep Learning Accelerator, freeing GPU cycles for other pipeline stages — at DLA's own throughput ceiling
batched-push-timeoutnvstreammuxCaps how long the muxer waits for a full batch; lower reduces latency on sparse streams, higher improves batch fill on bursty ones
mux width/heightnvstreammuxSets the common batched resolution; unnecessarily high values inflate every downstream stage's cost for no accuracy gain
Tiler / OSD costnvmultistreamtiler, nvdsosdComposition and on-screen drawing scale with stream count and resolution — disable or lower-res them for headless/analytics-only deployments
sync=0sinkDisables clock-synchronised playback so the sink drains as fast as the pipeline produces frames — throughput over real-time display fidelity
In practice

Tune in this order: get precision and interval right first (biggest wins, cheapest to try), then batch-size and mux resolution, then trim tiler/OSD cost for the actual deployment target. Re-measure aggregate streams×fps after every change — the interactions between knobs are not always additive.

08

Debugging & observability

DeepStream inherits GStreamer's debugging toolchain wholesale, plus a few DeepStream-specific instruments for measuring what actually matters at deployment scale.

  • GST_DEBUG — the standard GStreamer log-level environment variable (GST_DEBUG=3 for warnings, higher for full trace); the first thing to raise when a pipeline fails to reach PLAYING or drops silently.
  • GST_DEBUG_DUMP_DOT_DIR — dumps the live pipeline graph (elements, pads, caps, links) to .dot files at each state change; render with Graphviz to see exactly what topology was actually built, which is invaluable when config-file groups silently fail to wire up.
  • gst-inspect-1.0 — lists an element's full property set, pad templates and capabilities; the fastest way to check a property name/type before it causes a silent no-op.
  • NVDS_ENABLE_LATENCY_MEASUREMENT — enables per-component latency stamping through the pipeline, surfaced via the metadata; combine with the perf-measurement/FPS probe to get both throughput and per-stage latency in one pass.
  • trtexec — profiles a standalone TensorRT engine outside the pipeline, useful for isolating whether a slowdown is the inference engine itself or something else in the graph.

Common pitfalls

  • Caps / memory-type mismatch — an element expecting memory:NVMM (GPU/unified memory) fed from one that outputs system memory; the link fails or silently forces an expensive copy.
  • Unexpected engine rebuilds — nvinfer rebuilds the TensorRT engine on the fly if the model, precision, or GPU compute-capability doesn't match the cached .engine file, costing minutes of startup latency on first run per target.
  • Batch-size mismatch — nvstreammux, nvinfer and downstream elements disagreeing on batch size produces truncated or misaligned per-frame metadata rather than an obvious error.
  • Queue placement — missing queue elements between GPU-bound stages serialise work that should overlap across threads; misplaced ones add buffering latency for no throughput benefit.
