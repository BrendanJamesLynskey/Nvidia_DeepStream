01

The toolbox at a glance

DeepStream ships 40+ Gst plugins (7.x–9.x) that plug into the standard GStreamer element model — each one a `.so` registered with `gst-inspect-1.0`. You compose the ones you need; deepstream-app's reference config wires a standard set for you, but nothing stops you building a leaner or stranger graph by hand.

02

Input & decode

Getting compressed video off the wire or disk and onto the GPU as raw NVMM-batched frames, without a CPU round-trip.

  • Gst-nvv4l2decoder — hardware decode on NVDEC. Handles H.264, H.265, VP9, MJPEG and more depending on platform; outputs directly into GPU memory (video/x-raw(memory:NVMM)) so nothing touches host RAM.
  • Gst-nvurisrcbin — a managed single-source bin wrapping uridecodebin-style source-plus-decode logic with DeepStream extras: automatic RTSP reconnection on drop, file-source looping, and smart-record (buffered pre/post-event clip capture) built in.
  • Gst-nvmultiurisrcbin — the multi-source evolution: manages N URI sources behind one bin, supports adding and removing sources at runtime (no pipeline rebuild), and exposes a REST control interface for live source management — the backbone of dynamic, fleet-scale deployments.
  • Gst-nvjpegdec — hardware-accelerated JPEG/image decode, for still-image and MJPEG-heavy sources.

uridecodebin itself (stock GStreamer) still works for quick prototyping — it auto-negotiates a decode chain from a URI — but it doesn't know about NVMM memory or DeepStream's reconnection/record features, so production pipelines almost always reach for nvurisrcbin/nvmultiurisrcbin instead.

03

Batching & routing

Inference is only GPU-efficient in batches. DeepStream's mux/demux pair is what turns N independent streams into one batched buffer and back again.

Gst-nvstreammux

Takes N per-stream buffer pads as input, forms a single batched buffer of configurable size, and attaches NvDsBatchMeta — the metadata root that every downstream plugin (nvinfer, nvtracker, nvdsanalytics, nvdsosd…) reads and writes. This is the plugin that makes shared-batch GPU inference possible at all.

The new nvstreammux (the config-driven low-level library introduced from DeepStream 6.2 onward) decouples batch size from source count: batches can be smaller or larger than the number of live sources, sources can join and leave without a fixed batch reshape, and per-source frame-rate/latency behaviour is configurable independently. It's the better fit for dynamic pipelines built on nvmultiurisrcbin.

Gst-nvstreamdemux

The inverse operation: splits a batched buffer back into N separate per-stream buffers, so downstream elements can go back to per-stream processing (e.g. per-stream encode-and-save after a shared inference stage).

04

Inference family

Four plugins cover the shape of a modern inference stage: engine execution, remote serving, custom pre-processing and detached post-processing.

  • Gst-nvinfer — runs a TensorRT engine in-process on the GPU; the default, lowest-latency path for detection and classification.
  • Gst-nvinferserver — routes inference through Triton Inference Server, in-process or over the network, enabling multi-framework models (PyTorch, ONNX, TensorFlow) and model-ensemble/versioning features Triton provides.
  • Gst-nvdspreprocess — builds custom or grouped-ROI input tensors ahead of inference, for models needing non-default scaling, per-ROI crops, or tensors assembled from multiple regions rather than the whole frame.
  • Gst-nvdspostprocess — parses raw inference output tensors into DeepStream metadata as a detached stage, useful when output parsing needs to live outside nvinfer's own parser hooks.
In practice

This slide is deliberately brief — engine building, INT8/FP16 calibration, primary/secondary GIE chains and the nvinfer/nvinferserver trade-off get a full deep dive in Part 04 — Inference & TensorRT/Triton.

05

Analytics & computer vision

Plugins that turn detections into understanding: identity over time, spatial rules, motion, geometry correction and mask visualisation.

  • Gst-nvtracker — multi-object tracking; assigns and maintains stable object IDs across frames on top of detector output. Pluggable low-level trackers (IOU, NvSORT, NvDeepSORT, NvDCF). Full treatment in Part 05.
  • Gst-nvdsanalytics — consumes tracker output to evaluate ROI occupancy, line-crossing counts, direction detection and overcrowding, all defined declaratively per-stream in config.
  • Gst-nvof + Gst-nvofvisual — hardware optical flow computed on the dedicated Optical Flow Accelerator (OFA) engine, with a companion visualiser that renders the flow vector field for debugging.
  • Gst-nvdewarper — corrects fisheye and 360° lens geometry, producing aisle-view or spot-view perspective-corrected outputs from a single wide-angle camera.
  • Gst-nvsegvisual — renders segmentation-model mask output as a viewable overlay.
06

Compositing & on-screen display

The plugins that make results visible — and the connective tissue (nvvideoconvert) that glues format-mismatched elements together throughout every pipeline in this series.

  • Gst-nvvideoconvert — colour-space conversion and scaling on GPU or the VIC (Video Image Compositor) engine on Jetson. The pipeline's universal adapter: whenever two elements disagree on caps, this is what sits between them.
  • Gst-nvmultistreamtiler — composites a batch of N streams into a single NxM tiled display surface, so a multi-camera batch can be rendered or encoded as one grid.
  • Gst-nvdsosd — draws bounding boxes, text labels, lines, polygons and segmentation masks directly from NvDsFrameMeta/NvDsObjectMeta — the last stop before metadata becomes pixels.
  • Gst-nvdsvideotemplate — a drop-in slot for custom CUDA or third-party library processing, letting you insert bespoke GPU logic into the pipeline without writing a full custom plugin.
07

Output & messaging

Two distinct output paths: pixels leaving as encoded video, and metadata leaving as structured events.

  • Gst-nvv4l2h264enc / nvv4l2h265enc — hardware encode on NVENC, the counterpart to nvv4l2decoder on the way out.
  • Gst-nvmsgconv + Gst-nvmsgbroker — the messaging pair: nvmsgconv converts NvDsEventMsgMeta into a schema payload (standard DeepStream JSON schema, or custom), nvmsgbroker publishes it to Kafka, MQTT, AMQP, Azure IoT or Redis. Covered fully in Part 07.

09

Reading a plugin

Every DeepStream plugin is a normal GStreamer element, which means gst-inspect-1.0 is the single most useful tool for working out how to wire one in: it lists pads, caps and every configurable property.

bash
gst-inspect-1.0 nvinfer

Look for two things in the output: the Pad Templates section, which shows sink/src caps such as video/x-raw(memory:NVMM) — confirming the element expects GPU-resident batched buffers, not system memory — and the Element Properties section, which lists every property (e.g. config-file-path, batch-size, unique-id) with its type, default and whether it's required.

In practice

A caps mismatch between two elements (e.g. one plugin emitting host memory, the next expecting NVMM) is the most common cause of a pipeline that builds but refuses to play. gst-inspect-1.0 <element> on both sides settles it in seconds.
