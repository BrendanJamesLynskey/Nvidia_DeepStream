01

The GPU Inference Engine (GIE)

Gst-nvinfer is the element that actually runs a neural network inside a DeepStream pipeline. It sits downstream of nvstreammux, takes the batched NvBufSurface the muxer produced, transforms it into whatever tensor shape and format the network expects, hands it to TensorRT for execution, and writes the results straight back onto the buffer as structured metadata — bounding boxes as NvDsObjectMeta, classifier outputs as NvDsClassifierMeta, and per-pixel masks as segmentation metadata hanging off the frame.

Crucially, none of this normally requires writing inference code. A Gst-nvinfer instance is configured entirely through a plain-text .txt config file — model path, precision, batch size, thresholds, class labels — and dropped into the pipeline as a GStreamer element like any other. The only code most projects write is a small output parser for a non-standard network head.

Key idea

nvinfer is a bridge, not a black box: it owns everything between "batched video frames" and "TensorRT engine call", and everything between "raw tensor output" and "queryable metadata" — buffer transform, batching, engine execution, and result attachment, all config-driven.

02

Primary vs Secondary GIE

A single nvinfer element can run in one of two roles, distinguished by process-mode. A PGIE (Primary GIE, process-mode=1) runs on the full frame, typically as an object detector. An SGIE (Secondary GIE, process-mode=2) runs on the objects an upstream GIE already found — cropping and batching each detected object's region for a second, narrower network, such as a make/colour classifier applied to every car a PGIE detected.

Which objects a given SGIE consumes is controlled by operate-on-gie-id (only look at objects produced by a specific upstream GIE, matched via gie-unique-id) and operate-on-class-ids (only look at specific detected classes, e.g. class 0 = "car"). Multiple SGIEs can chain off the same PGIE output — a colour classifier and a make/model classifier both reading the same set of car detections — and SGIEs internally batch the cropped object images together for one efficient TensorRT call, rather than one inference per object.

03

TensorRT under the hood

Every nvinfer instance is ultimately a wrapper around a TensorRT execution context. On first run, nvinfer takes the source model — typically an onnx-file, though UFF and Caffe are still supported on older paths — and has TensorRT build a serialized, hardware- and precision-specific .engine file: fusing layers, selecting the fastest kernel implementation for the target GPU, and laying out weights for the chosen precision. That build step can take minutes; the result is cached at model-engine-file so every subsequent launch loads the pre-built engine directly instead of rebuilding.

Precision modes

Set via network-mode: FP32 (0) is the accuracy baseline; FP16 (2) roughly halves memory and often close to doubles throughput on tensor cores with negligible accuracy loss; INT8 (1) goes further again but needs a calibration pass over representative data, supplied as int8-calib-file, to map float ranges onto the 8-bit dynamic range without wrecking accuracy.

DLA offload

On Jetson platforms with a Deep Learning Accelerator, `enable-dla=1` plus `use-dla-core` can move a supported network onto the DLA silicon entirely, freeing the GPU's CUDA cores for other GIEs or for the tracker/OSD stages running concurrently — a way to parallelise inference across dissimilar compute engines on the same chip rather than fighting for the same one.

Watch for

A cached .engine is tied to the exact GPU architecture, TensorRT version, precision and batch size it was built with. Change any of those — a driver/TensorRT upgrade, a different GPU SKU, a new batch size — and nvinfer detects the mismatch and silently rebuilds, which is why the first run after a deployment change is always slower.

The config file anatomy

A realistic primary-detector config, of the kind referenced from a pipeline's nvinfer element or a deepstream-app group:

config_infer_primary.txt
[property]
# hardware & model
gpu-id=0
net-scale-factor=0.0039215697
offsets=0;0;0
onnx-file=../../models/resnet18_detector.onnx
model-engine-file=../../models/resnet18_detector.onnx_b4_gpu0_fp16.engine
labelfile-path=labels.txt

# batching & precision
batch-size=4
network-mode=2
num-detected-classes=4
interval=0

# identity & role
gie-unique-id=1
process-mode=1
network-type=0

# post-processing
cluster-mode=2
model-color-format=0
network-input-order=0
maintain-aspect-ratio=1

[class-attrs-all]
pre-cluster-threshold=0.2
nms-iou-threshold=0.5
topk=20
KeyWhat it controls
gpu-idWhich physical GPU this GIE instance executes on, on multi-GPU hosts.
net-scale-factor / offsetsPer-channel scale and mean subtraction applied while converting the input buffer into the network's tensor.
onnx-fileSource model; TensorRT builds a serialized engine from it the first time it's needed.
model-engine-fileCached .engine path — skips the (slow) build step on every subsequent launch.

network-type0 detector, 1 classifier, 2 segmentation, 100 other/custom.
cluster-modeBounding-box post-processing algorithm — see next slide.
05

Pre-processing & output parsing

nvinfer handles both ends of the inference call: turning a raw video buffer into the tensor the network expects, and turning the raw tensor output back into usable metadata.

Input normalisation

net-scale-factor and offsets implement (pixel − offset) × scale per channel — the standard mean-subtraction/rescale most vision networks train with. model-color-format selects RGB/BGR/greyscale, network-input-order selects NCHW vs NHWC tensor layout, and infer-dims fixes the network's expected input resolution; nvinfer resizes and colour-converts on the GPU via the same VIC/CUDA path used elsewhere in the pipeline, so no host round-trip is needed.

Bounding-box clustering

A detector head typically emits far more raw candidate boxes than real objects; cluster-mode picks the algorithm that collapses them:

ValueModeNotes
0Group RectanglesOpenCV-style overlap grouping; simple, legacy default.
1DBSCANDensity-based clustering; copes well with irregular overlaps.
2NMSStandard IoU non-max suppression — the common modern default.
3NoneRaw boxes passed through unclustered, for a fully custom downstream parser.
4DBSCAN + NMS HybridDBSCAN groups, NMS trims within groups; highest quality, most compute.

Custom output parsing

Non-standard heads — anchor-free detectors, unusual segmentation formats, exotic classifier outputs — are handled by supplying parse-bbox-func-name and custom-lib-path, pointing at a shared library implementing the NvDsInferParseCustomFunc signature. For inputs that need bespoke, ROI-based or multi-tensor preparation before a network even sees them — e.g. feeding several regions of one frame as separate batch entries — Gst-nvdspreprocess sits upstream of nvinfer and writes a ready-made input-tensor-meta that nvinfer consumes directly, bypassing its own default pre-processing.

06

Batching, interval & throughput

Two knobs dominate inference throughput tuning. batch-size should generally match the nvstreammux batch size (the number of streams feeding the PGIE) — a mismatch leaves either GPU cycles or streams unfed, since one TensorRT call processes the whole batch together. For an SGIE, batch size instead bounds how many cropped objects are inferred per call, which can spike well above the stream count on busy frames.

interval=N skips inference on N frames after each one that's run, letting the tracker (Part 05) carry detected boxes forward by prediction rather than re-running the network on every frame — a direct accuracy-for-throughput trade that's one of the highest-leverage settings in a production pipeline.

intervalInference cadenceEffect
0Every frameMaximum detection accuracy and freshness; maximum GPU cost.
1Every 2nd frameTracker predicts the skipped frame; roughly 2× inference throughput.
4Every 5th frameGood for slow-moving scenes; tracker bridges longer gaps between detections.

The other lever is placement: on Jetson, splitting GIEs across GPU and DLA (Slide 03) lets independent networks run concurrently rather than serialising on one engine, which matters more than raw batch size once a pipeline runs several PGIE/SGIE stages per stream.

07

Triton via Gst-nvinferserver

Gst-nvinferserver is the drop-in alternative to Gst-nvinfer: same role in the pipeline, same metadata contract, but inference is delegated to the Triton Inference Server instead of a directly-loaded TensorRT engine. Reach for it when you need model frameworks TensorRT doesn't natively run (TensorFlow, PyTorch/LibTorch, ONNX Runtime), model ensembles (chained or parallel models served as one logical request), or dynamic batching and hot-swappable versions out of a Triton model repository.

CAPI mode

Triton runs in-process inside the DeepStream application via its C API — no network hop, latency close to native nvinfer, but the server shares the pipeline's process and GPU.

gRPC mode

A standalone Triton server (local or remote) is called over gRPC — decouples and can scale inference independently of the DeepStream pipeline, at the cost of a network round-trip per request.

Configuration is a protobuf text file (config.pbtxt-style) rather than nvinfer's flat key=value format, referencing the Triton model repository and specifying which backend, input/output tensor bindings and batching behaviour to use.

08

Custom models & TAO

Most production pipelines don't start from a model trained from scratch. NVIDIA's TAO Toolkit ships a catalogue of pretrained, DeepStream-ready models purpose-built for common perception tasks: PeopleNet (person/face/bag detection), TrafficCamNet and DashCamNet (vehicle detection from fixed and moving cameras), LPD/LPR (license-plate detection and recognition), and PoseClassificationNet (action/pose classification on top of body keypoints) — all designed to slot straight into an nvinfer PGIE/SGIE config with published label files and calibration data.

The TAO workflow

Train (or fine-tune a pretrained checkpoint on site-specific data) → prune the network to cut redundant channels → quantise for INT8 → export to ONNX (or the legacy encrypted .etlt format, or a pre-built engine) → drop the exported artefact into an nvinfer config's onnx-file/model-engine-file and a matching labelfile-path. No pipeline code changes; the model swap is entirely a config-file edit.

In practice

For edge deployment at INT8, TAO's exported calibration cache travels with the model artefact, so nvinfer can build an INT8 engine on the target Jetson without needing the original training data on-device — important when the calibration set itself is sensitive or simply too large to ship to every edge box.

09

Takeaways

  • Gst-nvinfer is config-driven: model path, precision, batching and thresholds live in a text file, not application code.
  • PGIE (process-mode=1) detects on full frames; SGIE (process-mode=2) classifies or refines the objects a PGIE already found, gated by operate-on-gie-id/operate-on-class-ids.
  • TensorRT builds and caches a hardware- and precision-specific .engine from ONNX; it silently rebuilds whenever GPU, TensorRT version, precision or batch size change.
  • FP16/INT8 trade accuracy for throughput and memory; DLA offload parallelises inference across silicon on Jetson.
  • Bounding-box clustering mode and custom parser functions bridge nvinfer to non-standard detector/segmentation heads.
  • interval is the single highest-leverage throughput knob — skip inference frames and let the tracker interpolate.
  • Reach for Gst-nvinferserver / Triton when you need multiple frameworks, model ensembles, or an independently-scaled inference tier.
  • TAO Toolkit pretrained models give a fast, production-grade starting point without training from scratch.
