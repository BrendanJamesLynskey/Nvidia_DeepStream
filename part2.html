01

Why GStreamer

GStreamer is a mature, cross-platform, pipeline-based multimedia framework: two decades of production use, a plugin ecosystem covering nearly every container, codec, network protocol and rendering sink you'll ever need, and a runtime that already solves the hard, boring problems of dynamic pipeline construction, capability negotiation, multi-threaded scheduling, buffering and clocking.

NVIDIA's choice was pragmatic rather than novel: rather than inventing a bespoke media runtime, DeepStream ships as a family of GStreamer plugins — nvv4l2decoder, nvstreammux, nvinfer, nvtracker, nvdsosd and friends — that drop into an ordinary GStreamer graph alongside standard open-source elements (qtdemux, rtspsrc, h264parse). You inherit the entire ecosystem for free: file and network demuxing, container parsing, RTSP/RTMP ingest, and a battle-tested threading model.

What DeepStream adds on top is narrow but essential: hardware-accelerated elements that keep frame data resident on the GPU, and a shared convention for attaching structured, batched inference metadata to buffers as they flow through the graph. Strip away the AI branding and DeepStream is, architecturally, accelerated GStreamer elements + a metadata convention.

Key idea

If you already know GStreamer, you already know 80% of DeepStream's plumbing. The remaining 20% — NVMM memory and NvDsBatchMeta — is the subject of the rest of this part.

02

Core primitives

Five concepts carry almost all of GStreamer's vocabulary, and DeepStream reuses every one of them unchanged.

  • Elements — the unit of processing (a decoder, a filter, a sink). Each element exposes pads: a sink pad for data in, a src pad for data out.
  • Linking & caps negotiation — two elements are linked pad-to-pad; before data flows, they negotiate a shared capabilities (caps) structure describing format, resolution, framerate and memory type. Negotiation fails loudly if no compatible caps exist.
  • Bins & the pipeline — a bin groups elements into a reusable sub-graph; the pipeline is the top-level bin that owns the clock and drives the bus.
  • GstBuffer — the unit of media data flowing downstream, one per frame (or chunk), carrying timestamps and, in DeepStream, a pointer into GPU memory rather than raw host pixels.
  • Events & the GstBus — events (EOS, seek, caps changes) travel through the pipeline alongside buffers; messages (errors, warnings, state changes, EOS) travel upstream out-of-band via the GstBus to the application.
03

A pipeline is a graph

The fastest way to see DeepStream elements behaving as ordinary GStreamer citizens is gst-launch-1.0, the command-line pipeline builder every GStreamer developer already knows:

shell
gst-launch-1.0 \
  filesrc location=input.mp4 ! qtdemux ! h264parse ! nvv4l2decoder ! \
  mux.sink_0 nvstreammux name=mux batch-size=1 width=1920 height=1080 ! \
  nvinfer config-file-path=config_infer_primary.txt ! \
  nvvideoconvert ! nvdsosd ! nveglglessink

Read the syntax literally: ! is the link operator — it connects the src pad of the element on its left to the sink pad of the element on its right, triggering caps negotiation between them. name=mux assigns a handle to an element so later syntax can address it directly; mux.sink_0 is pad syntax (element_name.pad_name) used to request a specific pad on an element with multiple inputs — here, input stream 0 of the muxer.

Notice the graph shape: ordinary open-source elements (filesrc, qtdemux, h264parse) handle file I/O, demuxing and bitstream parsing exactly as they would in any GStreamer application. DeepStream elements (nvv4l2decoder, nvstreammux, nvinfer, nvvideoconvert, nvdsosd) slot in wherever hardware acceleration or inference is needed. Nothing about the framework changes — only which elements you choose to link.

04

NVIDIA hardware blocks

A discrete GPU or Jetson SoC exposes several fixed-function and programmable blocks alongside the CUDA cores. DeepStream's job is to expose each one through a plugin, so your pipeline's element choice is really a choice of silicon.

Hardware blockDoesDeepStream element(s)
NVDECFixed-function video decode (H.264, H.265/HEVC, AV1, VP9)nvv4l2decoder
NVENCFixed-function video encodenvv4l2h264enc, nvv4l2h265enc

VIC JetsonFixed-function scale, colour-space conversion, composite — offloads these from the GPUnvvideoconvert (VIC path on Jetson)
DLA JetsonDeep-learning accelerator; runs INT8/FP16 TensorRT engines in parallel with the GPUnvinfer with enable-dla=1

On Jetson especially, this mapping matters for throughput: routing scale/convert work through the VIC instead of the GPU frees CUDA cores entirely for inference, and offloading a secondary classifier to the DLA lets it run concurrently with a primary detector on the GPU rather than time-sharing the same compute.

05

The memory model — NVMM / NvBufSurface

This is the single most important architectural fact in DeepStream. Decoded frames are not delivered as host-memory pixel buffers that each plugin copies, transforms and copies back — they live in NVMM ("NVIDIA memory"), a GPU-resident (or Jetson unified-memory) surface described by an NvBufSurface structure. GstBuffers carry the caps feature memory:NVMM to advertise this, and downstream elements negotiate for it explicitly.

Because every DeepStream plugin understands NvBufSurface, what actually crosses a pad boundary is a pointer and metadata describing the surface — never the pixels themselves. Decode, inference, tracking, on-screen-drawing and encode all operate on the same underlying GPU allocation. This is zero-copy: no host↔device transfer, no per-stage memcpy, for the entire lifetime of a frame in the pipeline.

Batched, GPU-side scale/convert/composite operations on these surfaces — resizing to an inference network's input dimensions, colour-space conversion, cropping a batch of detected objects — go through NvBufSurfaceTransform (and its DeepStream wrapper, nvvideoconvert), which operates on N surfaces in one call rather than one frame at a time.

Key idea

Any time a pipeline mixes DeepStream elements with a plugin that only understands system memory, GStreamer inserts an implicit copy to satisfy caps negotiation — silently reintroducing the cost NVMM exists to avoid. Watch your pipeline graph for unexpected videoconvert (no nv prefix) elements.

06

How DeepStream extends GStreamer

NVMM solves where the pixels live. DeepStream's second contribution solves where the inference results live: a parallel, structured metadata channel that rides alongside each GstBuffer without polluting the buffer itself.

NvDsBatchMeta

A metadata tree attached to each batched buffer: one NvDsFrameMeta per source frame in the batch, each holding a list of NvDsObjectMeta (detections), which in turn can carry classifier results, tracker IDs and arbitrary NvDsUserMeta. Plugins read and append to this tree in place.

Batching at nvstreammux

nvstreammux collects frames from N input streams into a single batched buffer of a fixed batch-size. Every downstream element — nvinfer, nvtracker — then processes the whole batch in one call, amortising kernel-launch and inference overhead across streams instead of paying it per-stream.

Tiler / demuxer fan-out

At the end of the graph, nvmultistreamtiler composites the batch into a single tiled preview surface for display, or nvstreamdemux splits the batch back into N independent per-stream buffers — e.g. for per-camera recording or RTSP re-streaming.

Probes

A probe is a callback attached to a pad that fires on every buffer passing through it. Application code reads or edits NvDsBatchMeta from a probe — adding custom analytics, filtering detections, drawing overlays — without writing a custom GStreamer plugin at all. This is the primary integration point for DeepStream application logic.

07

Threads, queues & latency

GStreamer pipelines don't run as one thread by default — each element pushes and pulls on whatever thread it's scheduled on, and explicit queue elements are how you decouple stages onto independent threads, buffering between them so a slow downstream element doesn't stall a fast upstream one (or vice versa).

  • Pipeline latency is the sum of every element's processing and buffering delay; DeepStream applications query it via the GST_QUERY_LATENCY mechanism, same as any GStreamer app.
  • nvstreammux batch size trades latency for throughput: a larger batch-size improves GPU utilisation per inference call but means waiting for more frames to arrive before the batch is dispatched.
  • batched-push-timeout bounds that wait — the muxer pushes whatever it has once the timeout (microseconds) elapses, so one slow or dead source doesn't stall the whole batch indefinitely.
  • Live sources (RTSP, cameras) run the pipeline in "live" mode: the pipeline clock governs playback and late buffers are dropped rather than causing the whole graph to fall behind.
  • Sink synchronisation — sync=0 on a sink (e.g. fakesink, file sinks) processes buffers as fast as the pipeline can produce them, useful for benchmarking or offline batch jobs; sync=1 (the default for display sinks) paces output to the clock for real-time playback.
Key idea

Batch size and queue depth are the two knobs you'll tune most in production: too small and you leave GPU throughput on the table, too large and you add latency a real-time analytics pipeline can't afford.

08

The architecture, assembled

Put the hardware mapping and the metadata model together and the canonical DeepStream pipeline reads as two parallel tracks: pixels moving through NVMM on one, structured meaning accumulating in NvDsBatchMeta on the other — both riding the same GstBuffer downstream.

Key idea

Buffers carry pixels, resident on the GPU, moved by pointer. Metadata carries meaning, built up incrementally by each plugin as the batch passes through. Master this split and the rest of the DeepStream SDK — every plugin in Part 03 onward — is just detail on top of it.
